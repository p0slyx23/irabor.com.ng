The current site
is the reference.

I captured a fresh local production build in desktop and phone sizes before making these alternatives. Its identity is already recognizable. The job is to make the opening screen more useful, give projects a clearer hierarchy, and show the developer behind the work.

Keep the visual signature

The small stacked brandmark, Space Mono headings, almost-black background, compact navigation, and sharp offset buttons already belong together. A warm editorial serif, sage palette, or imitation workbench would discard that work.

Reduce the opening burden

The current two-line page heading and generous gap before the first image use much of the first screen to name a section. V2 brings your role and a featured project into the same opening composition.

Choose what leads

The captured homepage leads with Travel Booking Platform Backend. That is legitimate work, but if the goal is frontend hiring, lead with a project whose interface and your contribution support that goal. This is an editorial choice, not an automatic “newest first” sort.

More precision.
Less replacement.

The v2 foundation uses your existing design choices. The changes are in spacing, reading order, content density, and interaction. They should make the portfolio feel more considered without making it look like someone else’s site.

Keep these decisions

  • Your exact SVGs. White for dark surfaces, black for light. Keep their visual size consistent, including the footer.
  • Space Mono. Embedded in this report from Google Fonts’ official source. Use it for titles and selected navigation labels; let body copy stay easy to read.
  • Your theme palette. Dark background #080714; dark accent #FF50B3; light accent #7901B1. Keep images neutral rather than tinting project artwork.
  • Your button press. The existing 4 px offset shadow remains a recognizable detail. The active state moves into its shadow; keyboard focus is a separate visible outline.
  • Your real content. Actual projects, existing experience entries, existing posts, working email, and GitHub.

Improve these decisions

  • Role before categories. A first-time visitor should not have to open About to know you are a frontend developer.
  • Curate the homepage. Store a selected-project order explicitly, instead of letting generic sorting decide the first impression.
  • Contribution beside the cover. The product description explains the system; a short ownership statement explains why it belongs in your portfolio.
  • Fewer repeated stacks. Three compact tags are enough in a preview. Move full tool descriptions and stack carousels into the case study where they have context.
  • Separate reading and browsing widths. Wider images and project compositions, narrower article prose. A wider shell should not produce 120-character paragraphs.

Motion from your
actual interactions.

Your site already has navigation transitions, theme controls, project hover states, carousels, and reading progress. V2 should coordinate those behaviors. These timings are proposed design values, not performance measurements.

PROJECT LINK / 140–360 MS

Focus the artwork

A barely perceptible image scale (1 → 1.015), followed by a small arrow movement, is enough. Keep the cover’s edges stable. On touch, the link remains obvious without a hover. Reduced motion removes the scale.

PROJECT SWITCH / 180–220 MS

Keep the index still

For direction 02, replace the selected image and text while preserving the project-list position and keyboard focus. A production crossfade should never fade the list or move the active pointer target. The preview currently switches directly.

MOBILE MENU / 240 IN, 160 OUT

A controlled open and close

Make the header and menu controls feel like one composition. Keep the theme toggle next to close, as you requested. Use a real dialog or equivalent focus management; Escape and focus restoration must work.

THEME / ONE RESOLVED STATE

Keep color synchronized

The header control, open menu control, custom status strip, and theme-color metadata use one resolved theme. Avoid separate local state or staggered color timers. This HTML prototype demonstrates the shared state, not hardware status-bar behavior.

CASE STUDY / 280–320 MS

Connect cover to detail

In production, navigate to a dedicated project route and optionally preserve the cover’s visual continuity. The short dialog here exists only to inspect the prototype. No extra “loading” screen if the page is already available.

ARTICLE SCROLL / DIRECT

Reading progress that follows

Track the actual article, below the fixed header, without a lagging spring. Hide the line on short pages. Keep headings and a contents list so progress is not the only navigation cue.

The working previews support hover/press, project selection, category filtering, native dialog focus behavior, menu closing, and synchronized theme controls. The report’s “Reduce motion” control and the OS preference disable nonessential movement. The more elaborate route and menu transitions above are production specifications, not features falsely claimed to be implemented in every preview.

The content edits
that make v2 credible.

A visual update is strongest when the work becomes easier to understand. These are specific issues in the source material and captures, not a request to manufacture more content.

Project covers are context, not evidence

Your supplied covers look substantially better than placeholder illustrations. Keep them. But they combine headlines, feature lists, and device mockups into one image; they become hard to read on phones. Use them for overview, then add direct interface crops to the actual case study.

Primewave’s cover still says “In Development,” while your project data marks it completed. The report keeps the supplied artwork unchanged and calls out that mismatch in the project preview. Update the original artwork before publication.

Make ownership specific

“A role-based platform” is product context. “Designed the workspaces, built the React interfaces, and implemented the PHP workflows” explains your contribution when the project content supports it. Keep collaborative boundaries explicit and verify any shortened role statements before publishing.

Reconcile the role throughout the site

Your brand tagline is Frontend Developer, while some About and cycle text foreground product design and mobile. Lead consistently with frontend work; let the case studies show your range. You do not need to hide backend or mobile work.

Preserve useful depth

Experience, posts, snippets, and resources can remain. Show two project-related posts near the homepage close and place deeper archives on their existing routes. Keep the newsletter hidden until there is a functioning service and a publishing reason to ask for a subscription.

Avoid decorative proof

No fabricated business metrics, skill percentages, invented testimonials, or “available now” status. The prototypes use existing experience and project content; suggested homepage copy is clearly a presentation proposal.

I would build 01.

It respects what is already good and fixes the most important hierarchy problem. The homepage still leads with the work, but visitors see your role and your contribution sooner. It is also the least expensive option to maintain well.
