Lead with a role.
Prove the range.

My recommendation is to position you as a Frontend Developer, then demonstrate software and full-stack capability through what you built. Someone deciding whether to interview you should not have to interpret three equally prominent titles.

Suggested introduction: “I build clear, dependable web interfaces.” Follow with: “Frontend developer in Lagos, with experience across React interfaces, role-based workflows, PHP APIs, and mobile products.” This is proposed copy, not a new claim about your employment.

Interaction needs a job.

Use interaction to reveal how you think: inspect a component state, follow a booking flow, compare product constraints, or explore a decision. A pointer trail, typewriter biography, fake terminal, and continuously spinning stack logos communicate less.

The designs below use your existing Primewave, LGSC, and LugSpace material. They propose a presentation system, not new project results. No conversion gains, user counts, performance scores, testimonials, or product screenshots are invented.

My pick: The Interface Workshop

Choose direction 2 if your goal is frontend employment. It lets the portfolio itself demonstrate the craft you want to be hired for. Keep its demo scoped to one excellent component and write the case studies with the clarity of direction 1. That borrows a content discipline, not a second visual identity.

Visual system & composition

A publication-like page: an asymmetrical masthead, a compact identity block, and a ruled index of three selected projects. The type hierarchy replaces decorative containers. Each project opens into a long-form case study with margin notes for constraints, dates, and ownership.

Production type: a self-hosted editorial serif such as Newsreader for titles; a neutral sans such as Source Sans 3 for reading. The offline sketch uses Georgia and Segoe UI as explicit fallbacks, not the final type specification.

Homepage sequence

Role + selected project index → one detailed project excerpt → experience timeline → short working principles → email and résumé. Put supporting notes on their own route.

Behavior, motion & mobile

  • Desktop: selecting or focusing a project row changes the adjacent preview; do not move the pointer target or shift the list.
  • Motion: fade the preview over 160 ms and move its caption no more than 6 px over 200 ms. In reduced motion, replace immediately.
  • Mobile: place project imagery after its selected summary, and use explicit selection instead of hover-only previews. Avoid a two-column layout with tiny text.
  • Case study: keep “My contribution” near the top and show the live product link before the long narrative.

Where it can fail

It depends on excellent editing. Three vague “overview / challenge / solution” essays are weaker than one precise explanation of a tradeoff. Keep specific technical details and remove repetitive capability claims.

Effort: relatively light UI implementation; substantial copy and evidence work. Best when the work can stand still and still feel impressive.

Reference & reasoning: Brittany Chiang [R1] presents role, experience, projects, and writing in a clear sequence. Borrow the evidence hierarchy and scannability; do not copy her split layout, palette, cursor treatment, or wording.

Visual system & composition

A dark, tightly composed working surface with a pale product specimen. The homepage leads with a real component-sized demonstration, not an imitation code editor. Bright acid-green is reserved for the current state and focus. Documentation remains plain and highly readable.

#182426#E8EFDC#D7F785

Production type: a precise sans such as Instrument Sans; monospaced type only for code, measurements, or genuine API fields. Use 16–18 px body copy and a 48–72 px desktop headline.

Homepage sequence

Role + one live specimen → three delivered projects → an interaction breakdown → experience → short technical notes → résumé/contact. The demonstration supports the projects; it does not replace them.

Behavior, motion & mobile

  • State inspector: buttons change one specimen while maintaining its outer dimensions. Show textual feedback, not color alone.
  • Motion: 120 ms control feedback; 180 ms state crossfade. Use a restrained spring only for one draggable or expanding element where position matters.
  • Mobile: specimen below the introduction, state controls wrapping into two rows. Every state remains usable with touch and keyboard.
  • Production upgrade: add a width control to a sandboxed real component, plus a brief annotated code excerpt. Keep sandbox code separate from the navigation and theme shell.

Where it can fail

Four perfect states in a toy demo are not proof of production resilience. Pair the specimen with an actual component, its tests, and the limitations you handled. Never imply the synthetic fixture is a real customer booking.

Effort: medium. One excellent reusable demo is maintainable; a custom mini-app for every project is a second product to support.

Reference & reasoning: Josh W. Comeau [R2] treats interactive explanation as part of teaching frontend work. Borrow the “let me try the idea” principle, not his illustration style or blog identity. Applying it to your portfolio is my design recommendation.

Visual provenance: the booking specimen is original HTML/CSS authored for this report. Labels and state messages are simulated; it is not a capture of Primewave’s production interface.

Evidence to add: an annotated screen and the component you owned.

Visual system & composition

An atlas of product behavior, using purposeful diagrams, not decorative circuitry. Deep forest text, mint paper, ruled annotations, and numbered scenario steps make relationships readable. The main screen is a workflow beside an evidence panel; diagrams connect to detailed case studies.

#E7EDE9#19382C#214B35

Production type: Source Sans 3 for labels and body; a complementary serif for the main proposition. Code uses a mono face. Diagrams use the same label scale as the surrounding text.

Homepage sequence

Role + one product scenario → selectable system layers → project evidence → ownership and collaborators → experience → contact. A conventional “All projects” list remains one click away.

Behavior, motion & mobile

  • Inspect: selecting a layer exposes its responsibility, failure mode, and the artifact that demonstrates your contribution.
  • Motion: for a deliberate “Trace request” action, highlight steps over 600–900 ms once; keep the static route visible. No endlessly circulating particles.
  • Mobile: replace a horizontal graph with ordered vertical steps, followed by inline evidence. No pinch-to-read diagrams.
  • Accessibility: keep layers as semantic controls with a text equivalent; a canvas cannot be the only source of the workflow.

Where it can fail

A client-side role gate is never an authorization guarantee. Explain that the server must independently authorize actions; do not expose production endpoints, tokens, identities, or internal operational details in the public demo. The exact request path must be verified before publishing it as your architecture.

Effort: medium to high. Best when pursuing full-stack roles and able to substantiate boundaries, constraints, and failure recovery.

Reference & reasoning: The Pudding [R3] is a reference for explaining a subject through an interactive visual story. The atlas adapts that explanatory approach to software; it does not borrow their page designs or imply they endorse this concept.

Visual provenance: the layered flow is an original HTML/CSS diagram. React, PHP, and MySQL come from your project content; the illustrative layering is a proposal requiring technical verification.

Visual system & composition

A plum-black screening space with warm white typography and oversized product imagery. The cover occupies most of the first screen; short editorial captions provide enough context to understand what you did. The supporting pages are quieter, using the same color and type grammar.

#281C2B#F7ECDE#D4C2D4

Production type: a distinctive serif such as Bodoni Moda for short titles, paired with a restrained sans. Title scale comes from image hierarchy, not a headline that fills the entire viewport.

Homepage sequence

One featured project → compact index of all selected work → experience and delivery capabilities → a personal paragraph → résumé/contact. Project pages open with direct imagery, ownership, and links.

Behavior, motion & mobile

  • Signature transition: preserve the project image’s position when opening its case study; a 280–360 ms shared-image transition can make the navigation feel continuous.
  • In the sketch: previous/next changes the artwork and caption. A full production version can add a short manual transition; it must not auto-advance while someone reads.
  • Mobile: image before long details, visible next/previous controls, and normal vertical scroll. Swiping may supplement buttons but cannot replace them.
  • Media: use one opt-in silent interaction recording inside the case study. Ship a still poster first and include captions/transcript if audio communicates meaning.

Where it can fail

Large covers often hide thin case studies. Every image still needs a sentence about your role and a route to the evidence. Avoid scroll hijacking, giant preload percentages, automatic sound, and mandatory 3D navigation.

Effort: medium to high, mostly art direction and asset preparation. Strong for creative frontend roles; less useful if recruiters have to hunt for dates and experience.

Reference & reasoning: Bruno Simon [R4] demonstrates how a portfolio can be an interactive experience. Borrow the commitment to a recognizable idea. The screening room deliberately uses ordinary navigation rather than adopting his drivable world; 3D is optional only if it supports the work and you can maintain it.

Image provenance: embedded, unchanged covers from primewave-cleaning-cover.webp, lgscelection-cover.webp, and lugspace-cover.webp in your repository’s project image folder. These are your supplied artwork, not third-party inspiration screenshots.

Production type: a readable serif such as Literata for long-form pages, paired with a humanist sans for controls. Keep body copy around 65–75 characters per line and 1.5–1.7 line height.

Homepage sequence

Identity + featured shipped project → three newest substantive notes → experience → small topic index → contact. The final homepage must still introduce the developer before presenting an archive.

Behavior, motion & mobile

  • Search: match titles and topics locally; preserve the query in the final URL so a collection can be shared. Announce result counts without moving keyboard focus.
  • Progressive disclosure: open a short note summary inline; long articles always get a stable route with their own title and social preview.
  • Motion: a 140 ms link underline or 180 ms disclosure transition is enough. Reading progress belongs only on substantial articles and never covers the header.
  • Mobile: identity becomes a compact intro; search and the note list follow in normal reading order. No sideways library shelf or hover-only summaries.

Where it can fail

Do not manufacture a publishing cadence. Turn one actual project decision into a short note when you have something useful to show. Replace relative “Today” labels with dates calculated from real content timestamps, with an absolute date available.

Effort: moderate initial structure; high editorial commitment. A good secondary layer today, or a full direction if sharing technical thinking becomes part of your practice.

Reference & reasoning: Maggie Appleton [R5] distinguishes essays, notes, and other forms in a digital garden. Borrow the freedom to publish useful smaller thoughts and connect them; keep your own voice and do not imitate her illustration language.

Honor the operating system’s prefers-reduced-motion setting and offer an in-site control [R6–R7]. In this report the control can only reduce motion further; it never overrides an OS request for less motion. The replay demo illustrates easing, not a prescribed entrance for every section.

What to leave out

  • Scroll hijacking and forced horizontal reading.
  • A custom cursor that replaces the normal pointer.
  • Autoplay sound, endless marquees, or moving body text.
  • A loading screen when the content is already available.
  • Magnetic buttons that move away from the intended target.
  • Decorative code or terminals that don’t reveal your actual work.

Small details worth doing

  • Hover, focus, active, disabled, loading, empty, error, and success states.
  • Clear external-link and résumé behavior; do not make everything a new tab.
  • Stable image dimensions and graceful missing-image treatment.
  • Consistent menu, theme, and safe-area handling on actual phones.
  • Useful link text, keyboard order, selection colors, and text wrapping.
  • Meaningful recovery when a demo, network request, or form fails.

The missing layer is proof.

Your repository already carries projects, experience, posts, snippets, and resources. The largest opportunity is to connect them into a clear argument for hiring you. More sections alone will not make that argument stronger.

One case study, properly edited

  1. One-sentence product context. Who uses it and what they need to do.
  2. Scope and ownership. Exact role, collaborators, dates, and what was not yours.
  3. The hard decision. Constraint → alternatives → choice → tradeoff.
  4. Evidence. Annotated screen, code excerpt, workflow diagram, or recording.
  5. Validation. What you tested, on which devices, and what changed afterward.
  6. Outcome. A documented qualitative result is valid. Add numbers only when a source exists.
  7. Next step. Live product, permitted source, related note, or email.

Build the smallest convincing version.

First · Evidence

Choose three projects you can discuss deeply. For each, collect one desktop view, one mobile view, a relevant state, and one difficult decision. Confirm dates, ownership, publication permissions, and completed status. Choose the role headline before editing the homepage.

Then · Foundation

Keep your existing React/Vite foundation. Create tokens for type, spacing, color, focus, and motion. Reuse a single project data model across cards, case studies, notes, and search. Avoid a new UI or animation dependency until the chosen interaction requires it.

Then · One slice

Build one homepage opening and one complete case study at desktop and phone widths. For the Workshop, implement one accessible interactive specimen using isolated fixture data. Validate the content hierarchy before producing every other page.

Then · Finish

Add experience, résumé, contact, related notes, metadata, and useful 404s. Put each demonstration behind progressive enhancement. Only after the reading and navigation work should you add the signature motion.

Finally · Measure

Observe whether a reader can identify your role, name a shipped project, describe your contribution, and find your résumé without coaching. Fix confusion before adding effects. Measure performance in a deployed environment and preserve a simpler path for slow devices.

Engineering boundaries

  • Content: a reusable schema with title, summary, role, dates, technologies, evidence, links, and optional measured results with their source.
  • Demos: fixture data in isolated modules. No customer data, API keys, or real payments. Clearly distinguish a demo state from a production service.
  • Theme: one source of truth; no separate state in the status strip or mobile menu. Apply the initial theme before visible content to avoid a flash.
  • Contact: start with a working email link. A form needs validation, delivery feedback, spam controls, and minimal data retention.
  • Maintainability: plain CSS for small transitions; the existing motion library only where enter/exit or interruptible layout behavior earns it.

Performance targets, not invented scores

Aim for “good” Core Web Vitals at the 75th percentile: LCP ≤ 2.5 s, INP ≤ 200 ms, and CLS ≤ 0.1 [R8]. Those are launch targets, not measured results for your site.

Start with a self-imposed mobile first-load budget of roughly 1 MB transferred and 200 KB compressed JavaScript, excluding opt-in videos and résumé downloads; revise against actual assets and field data. Use responsive AVIF/WebP, reserve aspect ratios, lazy-load below-fold media, and self-host a limited set of font weights.

The standalone report embeds all covers for portability. That delivery choice is appropriate for a document, not a recommendation to embed base64 project images throughout the production site.

A launch checklist that means something.

A “20/20 audit” is not a meaningful guarantee without defined checks and evidence. These are twenty concrete acceptance checks for the eventual portfolio. They are a proposed launch gate, not a claim that all twenty have been run on your live site.

  1. Role and value are clear in the first viewport.
  2. Three selected projects have specific contribution statements.
  3. Project dates, status, cover labels, and résumé agree.
  4. Outcomes are sourced; no fabricated metrics or endorsements.
  5. Navigation, résumé, email, and external links resolve correctly.
  6. Every primary task works with keyboard alone.
  7. Menus handle focus, Escape, and focus restoration.
  8. Text, controls, and focus indicators meet the chosen WCAG contrast requirements.
  9. Touch controls aim for 44 × 44 px; verify WCAG 2.2 AA’s 24 × 24 px minimum and applicable exceptions [R9].
  10. No horizontal page overflow at narrow widths or with long titles.
  11. Content remains usable at 200% text zoom and under reflow testing.
  12. Reduced motion disables nonessential displacement and autoplay.
  13. Theme switches stay synchronized with the custom status strip and menu.
  14. Images have appropriate alt text, dimensions, and fallback behavior.
  15. Loading, empty, failure, retry, and success states are honest.
  16. Core Web Vitals are measured; lab and field results are distinguished.
  17. Private project data is redacted and public demos use safe fixtures.
  18. Each page has a useful title, description, canonical URL, and share image.
  19. 404s, reloads on deep links, offline failure, and disabled JavaScript have deliberate fallbacks.
  20. Check a real iPhone and Android device, Safari, Chrome, Firefox, and a screen reader before claiming broad support.
